# 窗口退出判定：现状与稳定性计划

2026-10-11。本文记录跨 Space、全屏窗口关闭后的判定依据和后续改进顺序；不是 macOS 提供了“最后一个窗口”的统一接口。应用各自决定关闭、隐藏和退出行为，无法确定时应保留原有关闭行为，不主动退出。

## 当前已验证的路径

- 红色按钮和可选的 `⌘W` 先交给目标 App 正常处理全屏关闭，再延迟检查；全屏分支连续两次确认 AX 标准窗口数、当前屏幕 CG 窗口数，以及跨 Space 的近屏幕尺寸 CG 窗口数均为零，才请求退出。
- 跨 Space 检查使用 CG `optionAll`。被关闭的窗口 ID 即使关闭后仍短暂留在列表，也不计作“其他窗口”。这解决了 Windows App Beta 的两个实测场景：其他 Space 尚有全屏窗口时不误退出；最后一个全屏窗口关闭后能退出。
- 当时观察到同一窗口 ID 在全屏时约为 `1800×1130`，关闭后残留条目约为 `1800×1076`；屏幕 `1800×1169`。当前的 `95%` 屏幕尺寸筛选由此而来，仅是启发式规则，不保证适用于所有显示器布局和 App。

## 本轮留痕

- 增加 `CloseMonitor` 的统一日志：仅记录触发来源、PID、目标窗口 ID、每次检查的窗口数量、是否请求退出及请求是否被接受；不记录窗口标题或内容。`-1` 表示该次窗口数量不可读取。
- 增加连续两次确认、跨 Space 有另一个窗口和残留目标窗口的规则测试。本轮不改变已验证的退出判定条件。
- 排查时可运行：`/usr/bin/log stream --info --style compact --predicate 'subsystem == "com.yinzhenyu.smartclose" && category == "CloseMonitor"'`。排查结束后停止命令；日志中含 PID 和窗口 ID，不要直接公开完整日志。

## QSpace Pro 的 `⌘W` 现场（2026-10-11）

- 关闭前：QSpace Pro 只有一个 AX 标准窗口和一个当前屏幕 CG 窗口；关闭后仍在运行，但两者均为零，跨 Space 列表只剩菜单栏尺寸条目。
- 两次复现均记录了 `source=keyboard kind=standard` 候选，却没有进入原先的第一条关闭后采样日志。因此缺口位于延迟检查的前置条件或 AX 读取阶段，不能据此断言一定是 AX 超时。
- 本次加入前置条件取消原因及 AX 错误码日志；AX 列表暂不可读时有限重试，不把不可读当作零窗口。新构建实测首次检查返回 `-25204`（`kAXErrorCannotComplete`），随后两次检查读到 AX 窗口数为零，正常请求退出；用户确认 QSpace Pro 已自动退出。

## 后续改进顺序

1. **窗口 ID 绑定**：目前全屏目标 ID 来自该 App 在当前屏幕上第一个近屏幕尺寸窗口，未严格绑定点击的 AX 窗口。先用点击位置、窗口边界与 AX 窗口信息做只读对照，覆盖多显示器和叠层窗口；只有能唯一匹配时才替换现有取值。无法唯一匹配时保守跳过自动退出。
2. **`⌘W` 的跨 Space 安全性**：普通窗口分支在 `AXWindows == 0` *或*当前屏幕 CG 窗口数为零时判定为空，后者可能漏看其他 Space；但这个条件也支持 Discord 等隐藏窗口的行为。先收集“普通窗口 + 其他 Space 全屏窗口”、Discord 隐藏、Firefox 关最后标签页等实测快照，再设计不会破坏隐藏窗口支持的跨 Space 否决条件。
3. **通知辅助复核**：评估 AX 窗口创建／销毁和 Space 切换通知，仅用于提前重新采样或取消待决请求。AX 通知可能不受目标 App 支持，因此仍保留定时复核与读取失败时不退出的原则。

每一步均需分别验证：单个全屏窗口、同 App 两个全屏窗口、被其他 App 的 Space 隔开的两个全屏窗口、全屏加普通窗口、多显示器，以及 `⌘W` 的上述三类行为。先通过规则测试和构建，再用真实 App 做手动验证；仅靠规则测试不能证明跨 Space 的系统行为。
