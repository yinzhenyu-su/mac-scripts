## Context

Ventoy 的倒计时弹出实际成功，卷已经从 `/Volumes` 消失，但菜单显示「1 个任务未完成：Ventoy 未弹出」。旧实现复查的是「整盘设备节点是否还在」：

```swift
if let bsdName = action.target.diskBSDName, DiskCatalog.isDiskPresent(bsdName: bsdName) {
    return true
}
```

`diskutil eject` 返回成功时卷已经卸载，但 DiskArbitration 的设备节点可能还要几秒才消失。2.5 秒的复查窗口正好撞上这段残留，于是成功被判定为失败。误报条目之后也不会自动消失，因为 tick 只处理 `armed`，`refused` 会一直留在状态行。

## Goals / Non-Goals

**Goals:**

- 成功弹出不再因为设备节点残留被误判。
- 目标已经消失的未完成任务自动清理，状态行不会卡住。
- 不改变弹出实现与数据结构。

**Non-Goals:**

- 不改变 `diskutil eject` 的调用方式，也不引入强制弹出。
- 不追求「设备节点必须消失」才算成功；用户可见的结果是卷已卸载。

## Decisions

### 1. 以卷是否仍挂载作为成功标准

用户能感知的是卷是否还在 `/Volumes`、是否还能读写；设备节点是内核层的实现细节。`diskutil eject` 返回 0 且卷已卸载，就视为成功。

备选方案：

- 延长复查窗口或轮询设备节点：只能降低概率，仍会在慢设备上误判，而且会推迟结果，否决。
- 保留设备检查，但设备残留时算成功：逻辑更绕，且与「卷卸载」这个真正的用户结果不一致，否决。

### 2. 未完成任务在目标消失后自动清理

每次 tick 除了处理 `armed`，还检查 `refused`：

- 磁盘：卷不再挂载 → 移除条目。
- 应用：进程不再运行 → 移除条目。

这样即使上一轮因为竞态误标了未弹出，卷/应用消失后状态行也会自动恢复，不需要用户重启。

## Risks / Trade-offs

- **[部分弹出被当成成功]** → 卷已卸载但设备节点仍在，用户看到磁盘从菜单消失；即使设备还挂在系统里，也可以安全拔出。`diskutil` 返回 0 是这一判断的前提。
- **[清理过早]** → 只清理目标确实不存在的条目；目标仍在时保持未弹出，不影响手动重试。
- **[应用任务被自动清理]** → 应用被用户手动退出后，未退出提示已经没有意义，清理是合理的。

## Migration Plan

无数据结构变化，随 1.6.1 发布即可。
