## Context

参见 `proposal.md - Why`。当前实现与本次改动相关的事实：

- 菜单项「应用规则说明」调用 `openRuleGuide()`，打开 `RuleGuideView`（标题、模式说明、当前列表、权限提示、三个按钮）。
- 同一个窗口也是首次引导：`store.needsOnboarding` 为真时由 `showRuleGuideWhenReady()` 自动展示。
- `RuleGuideView` 与 `onboarding.*` 文案仍被首次引导使用，删菜单项不影响它们。
- 「应用规则…」窗口已经包含：模式单选框、当前生效列表、底部行为说明（`settings.description` / `settings.footer.exclude` / `settings.footer.only`）。
- 主规格 `openspec/specs/application-rule-onboarding/spec.md` 的「引导状态及重新访问」要求里写明"用户 SHALL 能从菜单栏重新打开规则说明"，并带一个「手动重新访问」场景。
- 校验器要求 MODIFIED 需求必须保留原规格里已有的场景名，不能悄悄删掉。

## Goals / Non-Goals

**Goals:**

- 菜单少一行，规则相关信息只有一个入口。
- 首次引导行为完全不变。
- 规格改动最小：一条要求、一个场景名保留、一个新场景。

**Non-Goals:**

- 不删除 `RuleGuideView`、`openRuleGuide` 或 `onboarding.*` 文案。
- 不改动引导的持久化、异常退出重弹、升级保护与授权一致性。
- 不重做「应用规则…」窗口的布局。

## Decisions

### 1. 只摘菜单入口，保留窗口与首次引导

```
  删除：addAssistiveSection() 里的一行
  保留：openRuleGuide() / RuleGuideView / onboarding.*
  保留：needsOnboarding 触发的首次自动展示
```

删除整条链路（包括窗口）会连带影响首次引导与 onboarding 规格里的四条要求，收益为零。

### 2. 再访问入口改为「应用规则…」窗口

规则说明窗口的独有内容只有一句"阅读本说明无需授权"。模式解释、当前列表、关闭行为说明在规则窗口里都有对应物。因此把"重新访问"的落点改成规则窗口是等价的，不需要新增按钮或界面。

替代方案"在规则窗口加一个「说明」按钮再弹引导窗"被否决：那只是把菜单里的一行挪进窗口里的一个按钮，没有减少概念数量。

### 3. 规格用 MODIFIED 就地改写，保留原有场景名

校验器要求 MODIFIED 保留原场景名，因此「手动重新访问」这个名字保留，只改 WHEN/THEN：

```
  旧：WHEN 用户从菜单栏打开规则说明
      THEN 展示当前列表而非重新套用默认值

  新：WHEN 用户从菜单打开「应用规则」窗口
      THEN 看到当前模式、生效列表与关闭行为说明，且已有设置保持不变
```

另外新增「菜单不再提供独立入口」场景，把"菜单里没有这一行"变成可验证的契约。

## Risks / Trade-offs

- **[用户失去一个"只读"入口]** → 规则窗口本来就不需要授权也能打开（只是编辑被拦），阅读能力没有丢失。
- **["阅读本说明无需授权"这句话消失]** → 首次引导仍会展示它；已处理引导的用户不需要再被提醒。
- **[要求名仍叫「引导状态及重新访问」]** → 再访问仍然存在，只是换了落点，名字不算失真；避免 RENAMED + MODIFIED 叠加带来的归档复杂度。
- **[菜单项被删但窗口还在]** → 代码里 `openRuleGuide` 只被首次引导路径调用，不会成为死代码；`onboarding.title` 仍被窗口使用。

## Migration Plan

1. 删除菜单项，其余代码路径不动。
2. 验证：新用户首次启动仍弹出引导；已处理用户重启不再弹出；菜单中无「应用规则说明」，且「应用规则…」窗口内容完整。
3. 回滚：恢复菜单项即可，无数据迁移。

## Open Questions

- 是否要在「应用规则…」窗口底部补一句「编辑规则需要有效试用或 Pro」。免费用户点击入口时已经被拦到许可证窗口，这句话的价值主要是"先说明再拦"，可以等实际反馈再决定，不影响本次规格。
